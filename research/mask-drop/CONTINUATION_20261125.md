- 기존 문서에서는 두 숫자를 일반적인 1번 시작 2열 배열로 정규화했지만,
  네이티브 저장 구조에서는 첫 요소가 nil이므로 표준 `ipairs`는
  현재 표면상 **0개 항목**을 순회한다. 단, 런타임의
  `getCfgByNpc`/테이블 복원 결과가 파싱 원형과 동일한지 확인이 필요하다.
- 실제 PC38은 `getCfgByNpc.drop`에 대한 `ipairs`를 시작하고,
  PC41에서는 현재 인덱스를 사용하여 `getEncryptByNpc.drop` 항목을 읽는다.
  양쪽 테이블 역할을 바꾸거나 1:1로 동일하다고 가정하지 않는다.
- `JHCharUtils`의 원본 함수들 중 `getEncryptByNpc` 관련 프로토타입에는
  `getConfig('char_data')`, `ngx.clone`, `ngx.encrytTable` 상수가 확인된다.
  따라서 암호화/정규화 경로 재현 없이 원본 `drop` 쌍의 숫자 1을
  실제 추첨 가중치로 승격할 수 없다.
- 원본 `equipment_60014.sb3`에는 7209 수라가면
  **장비 테이블 항목**이 있고, 3031은 `item_60014.sb3`의
  **헝겊 조각**이다. PC79–96의 `getClass` 분기가
  두 번째 가중치 추첨을 사용하는지 추가 검증해야 한다.
- `original-60014-weight-tables.cjs`에서 잘못된
  `encryptedDropMatchesSource:true ⇒ [1,99]` 자동 변환을 **제거**했다.
  실험용 배열을 **명시적으로 제공**해야만 가중치 가설을 시험하며,
  원본 확정 결과로 표기하지 않는다.
- 합성 회귀 검사를 GitHub 연구 브랜치 CI로 실행하여 통과 확인했다.
  배포 UI와 메인 브랜치 변경 없음.

**중요:** 여기서 확인한 것은 원본 파일의 *배열 저장 형태와 정적 호출 관계*다.
게임 런타임에서 수라가면이 드랍되지 않는다는 뜻이 아니다.
게임의 원본 엔진과 실제 결과가 반대라면 설정 테이블
로드·복호화·런타임 정규화의 누락이 가장 먼저 의심된다.
첫 획득 회차는 여전히 미확정이다.


## 원본 함수 추가 추적과 실행 조건 강화

- `JHCharUtils_13.sb3`를 직접 확인했다. 원본 getEncrypt 관련
  프로토타입에는 `getConfig('char_data')`, `ngx.clone`,
  `ngx.encrytTable` 호출이 있다. 이 정규화/복호화 경로를
  실제 런타임과 동일하게 재현하기 전에는 정적 `drop`을
  `weightRand`의 가중치 배열로 취급하지 않는다.
- 원본 `JHAIClient.getDropByID` PC38–50은
  `getCfgByNpc.drop`에 대해 `ipairs`를 실행한 뒤,
  현재 인덱스를 기준으로 `getEncryptByNpc.drop`의 값을
  참조하고 가중치를 누적한다. **정적 `drop` 저장 형태의
  첫 번째 슬롯이 비어 있는 문제**가 해결되어야 한다.
- `JHTaskStatements_60014.sb3`(887개 프로토타입),
  `JHNetServer_60014.sb3`(37개),
  `JHDataCenter_60014.sb3`(677개)의 상수 테이블을
  직접 스캔했지만, 대상 NPC 30681/32950와 아이템 7209가
  숫자/문자열 리터럴로 나타나지는 않았다. **스캔한 이
  세 모듈에 한정된 부정 결과**이며, 외부 전투 이벤트나
  설정에서 값을 전달하는 경로는 아직 배제하지 못한다.
- `conditionalNpcStages`는 첫 추첨 범위를 계산하려면
  `runtimeCfgRows`(실제 NPC 드랍 행 ID)와
  `runtimeEncryptedRows`(같은 행에 대응하는 복호화 가중치)를
  **동시에 명시**하도록 수정했다. 행 정렬이 다르거나
  한쪽만 존재하면 오류로 처리한다.
- 합성 단위 테스트와 연구 브랜치 CI가 최종 커밋
  `78564fe`에서 **성공**했다. 이는 원본 런타임
  예측 적중 검증이 아니라 회귀 테스트 성공이다.

### 여전히 필요한 단 하나의 핵심 연결

동일한 NPC의 런타임 `getCfgByNpc.drop`과
`getEncryptByNpc.drop` 구조를 원본 60014 함수로 획득하고,
`getClass(7209)`가 PC84 뒤의 두 번째 추첨을
실제 실행하는지 확인해야 한다. 그 전에는 수라가면
첫 획득 회차나 같은 필드의 실전 공유 여부를 확정하지 않는다.

### 네이티브 원본 비교 (V182)

Library `60014_DROP_NATIVE_ARM64_RUNTIME_V182_20261012.zip`에 보존된
한국판 60014 AArch64 `libcocos2dlua.so`를 확인했다.
이 파일은 원본 60014 split의 19,480,304-byte native 라이브러리이며
기존 검증된 LuaJIT 2.1.0-beta3 정보가 있다. 그러나 평문 심볼 스캔으로
`encrytTable` 또는 `getEncryptByNpc` 구현을 식별하지 못했다.
**해당 함수가 없다는 의미는 아니며**, stripped/obfuscated native
진입점의 실제 구현 분석은 아직 완료되지 않았다. 네이티브 복호화
규칙을 추측해서 강제로 [1,99] 또는 다른 드랍 회차를 만들지 않는다.


## 후속 연구: 수라가면 1%를 우선 가설로 유지하고 조건부 2단계 재생 (2026-11-25)

사용자의 드랍 경험상 1%가 가장 유력한 사전 가설이므로
**PC74의 100칸 중 1칸 적중**을 우선 조사한다. 이는 복호화

  계산, NPC30681/32950의 동일 레벨 후보 난수 경로를 이용하여
  세 가지 시나리오로 1차 당첨 후보 순번을 독립 계산한다:
  `never`, `on-mask-first-hit`, `on-any-first-hit`.
- 원본 PC74(동적 가중치), PC75~85(보상 선택/장비 getClass),
  PC96(고정 가중치 합 1111)를 **서로 다른 단계**로 취급한다.

  난수 원시값을 반환하거나 저장하지 않는다.
  합성 테스트와 CI 추가.
