# 벽유교 인간정로 구출 `roll` 원본 RNG 출처 및 해시 순회 검증 — 2026-11-24

## 이번에 원본에서 확인한 사실

60014 원본 `JHTaskStatementsSeedKeyRoll.sb3`(SHA256 `2b9c7561394f3ba1bd6a91d17de8a29f3044844d1afdb7872828fdf8cfe109af`)는 **서로 다른 실행 함수 2개**를 정의한다.

| 이벤트 명령 | 원본 prototype | 원본 난수 API | 호출 코드 PC |
|---|---:|---|---|
| `seedkeyroll` (관문 장비/색상) | 1 | `s_jhData.getRands().getRandBetween(...)` | `getRands` PC29, `getRandBetween` PC32 |
| `roll` (인간정로 구출 재료) | 3 | `s_jhData.getStoryRnd().intRand(...)` | `getStoryRnd` PC19, `intRand` PC22 |

따라서 `roll` 구출 보상은 **`Rnds.Sds.seed_byj`와 동일한 난수 호출이 아니다**. 일반 관문 시드 소비에 무조건 포함시키면 안 된다.

실제 보유 사용자 세이브 1122·1122v3·1123 입장 전·1124의 최상위에 **`StoryRnd.S`가 모두 존재**하며, 각각 해당 보스의 `seed_byj`와 별개의 숫자다. 이러한 별도 객체의 존재와 소스의 `getStoryRnd()` 호출은 서로 부합하나, `intRand`가 `S`를 어떻게 변화시키는지는 **아직 원본 구현을 확보하지 못했다**. 각 시드의 실제 수치를 공개 보고서나 코드에 남기지 않는다.

## 진입 이벤트와 가중치 키 순회

인간정로 원본 2개 복호화 이벤트(Whale record 1777/2150)에서는 다음 구조를 확인했다.

- 그룹 1 `roll` 단계 8: 빈 `{}` 테이블에서 **정확히 6개**의 문자열 키 `GetP('drop_byj_1')` ~ `GetP('drop_byj_6')`를 원본 `TSETS` 순서대로 삽입; PC 37,41,45,49,53,57.
- 그룹 2 `roll` 단계 9: **7개** 문자열 키 `GetP('drop_byj_7')` ~ `GetP('drop_byj_13')`; PC 65,69,73,77,81,85,89.
- 두 소스의 13개 지급 동작은 모두 일치한다. 원본 이벤트는 `glm_reward == 0`일 때 구출 보상을 실행한다.
- 기존 LuaJIT beta3 내용 해시·재해시 **모델** 기반 `pairs` 순회:
  - **그룹 1: 3 → 4 → 1 → 6 → 2 → 5**
  - **그룹 2: 7 → 8 → 10 → 9 → 13 → 11 → 12**
- 키 순회는 게임 원본 런타임에서 관측된 값은 아니다. 원본 키 타입·PC는 바이트코드로 검증, 노드 순회는 런타임 모델 값이다.

## 신규 조건부 계산

`byj_story_roll_conditional.py`는 실제 13개 보상 지급/카운터 증분 레지스트리를 사용하여 **두 그룹의 1부터 시작하는 난수 출력값별 누적 선택 구간**을 계산한다. 외부에서 **실제로 관측한** `intRand` 출력값을 제공했을 때만 보상 동작을 적용한다.

*빈 가중치 그룹의 `intRand(0)` 작동은 미확인*이므로 추첨 자체를 막는다. 그룹별 총가중치가 다르면 `intRand` 인수도 그 합계에 달라지며, 정상 게임 코드의 반환 범위가 1~총합인지도 해당 원본 API 구현으로 확인해야 한다.

검증: 원본 진입 스크립트 2개 키 타입·PC와 스토리/보스 RNG 분기, 구간 연속성·영(0) 가중치·두 끝값·입력 오류에 관한 **신규 11/11 단위검사 통과**. 기존 벽유교 보상 지급/퇴장·출시 관문 통합 테스트 **34/34 통과**. 이들은 **모델 및 소스 기반 검사**이지 실측 미획득 계정 관문 성공률이 아니다.

## 정확히 남은 병목

1. 한국판 60014의 `getStoryRnd` 객체가 사용하는 **`intRand` 원본 구현 및 StoryRnd.S 상태 전이 알고리즘** 복원. 현재 해당 코드는 확보한 Whale fun/event 파일에는 존재하지 않으며, `JHDataCenter`/스토리 난수 관련 다른 런타임 소스가 필요하다.
2. 원본 네이티브 LuaJIT 해시 테이블의 `pairs` 구현으로 두 그룹 순회 모델을 독립 검증하고 `intRand` 반환 경계 확정.
3. 인간정로 구출 *직전*과 보상 완료 *직후*의 스토리 난수·카운터 변화(다른 플레이 활동 없는 기록)를 토대로 실측 검증. 기존 전체 일자 단위 세이브는 그 사이 다른 활동이 섞여 있어서 이 추첨만의 시드 소비 회수로 판단할 수 없다.
