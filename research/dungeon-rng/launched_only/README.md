## 혼합 관문 RNG 레인 경계 방어 (2026-11-25)

`mixed_gate_schedule.py`는 매 관문 실행 **직전**의 상태를 깊은 복사로 보관하고, 실행 후 `gate_seed_boundary.py`로 출시 4관문의 **9개 보스/관문 전용 RNG 시드 레인**을 검사한다. 관문별 소유 시드 키에 비해 생산자 반환 키가 부족하거나 초과하면 즉시 중단한다. 원본 생산자가 반환한 시드와 실제 다음 상태가 다르거나 다른 관문의 시드가 예상 밖으로 변경되어도 조용히 다음 관문 예측을 이어가지 않는다.

실제 원시 시드값을 별도 로그로 출력하지 않고, 각 클리어 결과에 `seedBoundary`를 추가해 변경된 **시드 키 이름만** 기록한다. 이 장치는 **모델 내부의 관문 간 상태 전달 오류를 조기에 탐지**하는 안전장치이며, 실제 게임의 모든 필드·장비 옵션 RNG와의 독립성을 증명하지 않는다. 기본 필드 `aidrop*`/`mdrop`, `Rnds.Eds`에는 별도 가정을 추가하지 않는다.

합성 단위 검사 `python -m unittest test_gate_seed_boundary.py -v`: **10/10 통과** (타 관문 변경, 누락, 잘못된 생산자 키, 시드값 불일치, 자료형 오류 등). 원본 바이너리/개인 세이브가 필요한 통합 4관문 과거 저장본 회귀는 이 단위검사와 구분하며, 이번 수정만으로 실제 미래 드랍 정확도를 새롭게 입증한 것은 아니다. 한국 서버 미출시 관문과 공개 사이트·버전/V82는 변경하지 않음.

## 2026-11-25 — 유씨별원 고리의 열쇠(8915) 보유 양분기 장비 민감도

`liu_key_8915_branch_compare.py`는 **동일 시작 세이브·난수 시드·특수재료 누적 상태**를 두 개로 복사하고 숫자키 `GetP(8915)`의 미보유(0)/보유(1) 조건만 달리하여, 요청한 **출시 관문 혼합 순서 전체**를 각각 재생한다. 각 관문의 보스별 한국판 장비명·색상·미드랍, 달라진 보스 이름, 난수 호출 수 변동, 종료 시드가 달라진 레인 **이름만** 출력하며 시드 원문이나 계정 식별 정보를 출력하지 않는다. 새 코드는 `get_8915` (누적 지급 횟수)와 숫자키 보유 판정을 결코 동일시하지 않는다.

```bash
python liu_key_8915_branch_compare.py --before /private/BEFORE.json \
  --source-root /private/v30 --registry /private/gate-60-source-registry.json \
  --schedule 유씨별원,유씨별원,유씨별원
python -m unittest test_liu_key_8915_branch_compare -v
```

새 독립 합성 검사 **8/8 통과**: 양분기 차이, 보스별 한국판 장비 비교, 세이브 불변, 숫자 보유 판정과 `get_8915` 누적 분리, 시드 원문 비노출, 정상적으로 차이 없는 결과, 불완전/뒤바뀐 RNG 생산자 차단을 검증했다. 이것은 조건부 시나리오 비교 도구이지 실제 한국 서버가 `globalVariable['8915']`를 인벤토리 보유량으로 읽는다는 독립 증거가 아니다. 기존 v77 고리 열쇠 실측은 보유 시나리오를 지지하지만, 향후 세이브의 실제 소지 여부와 소비·지급 전이를 확정하지 않으며 **두 경로 중 하나를 정답으로 강제 선택하지 않는다**.

개인 세이브, 시드값, 사용자별 예측 출력, 공개 사이트/버전 및 미출시 관문 연구 로직 변경 없음.

## 2026-11-25 — 고리의 열쇠(8915) 회차별 명시 보유 상태

`mixed_gate_schedule.py`는 `--liu-key-ownership`을 선택적으로 받아 **유씨별원 클리어 회차별로** 숫자키 `GetP(8915)`의 모델용 보유 상태를 적용한다. 예: `--schedule 벽유교,유씨별원,창옥,유씨별원,유씨별원 --liu-key-ownership unheld,held,unheld`는 유씨별원 1·2·3회 직전에 각각 미보유·보유·미보유 가정을 적용한다. 이는 유씨별원 외 다른 관문에서는 키를 강제로 바꾸지 않는다.

**주의:** 사용자 실측의 실제 소지·사용 기록을 명시한 조건부 실험용이다. `get_8915` 누적 지급 횟수, `drop_8915_35264` 당첨 플래그, 지난 클리어 결과만으로 인벤토리 소유를 추론하거나 다음 회차의 열쇠 상태를 자동으로 갱신하지 않는다. 숫자키와 실제 한국 서버 소지품의 연결을 독립 검증한 것이 아니다. 옵션 미지정 시 기존 재생 동작 그대로. 상태 하나라도 누락되거나 `unknown`이면 거짓 0으로 대체하지 않고 오류를 반환한다.

연구 전용 검사 `python -m unittest test_liu_key_timeline test_gate_seed_boundary test_liu_key_8915_branch_compare`: **30/30 로컬 통과**, 그중 이번 회차 타임라인 전용 12개. 원본 세이브/추출 엔진이 이 실행 환경에 존재하지 않아, 실제 한국판 신규 미래 드랍 통합 회귀는 실행하지 못했다. 공개 사이트·V82·미출시 관문은 변경하지 않음.

## 2026-11-25 — v78 선행 복원 재확인 및 열쇠 소지 이력 기반 연속 재생

**중복 재구현 방지:** 과거 연구 체크포인트 `README_V78.md`와 `README_V79.md`에 이미 유씨별원 **고리의 열쇠 8915의 `Items` 시작 수량 확인, 신규 당첨 때만 수량 +1, 3회차 보유 상태 승계 및 실측 장비 3/3**이 기록되어 있음을 재확인했다. 이번 변경은 그 결과를 새 발견으로 주장하지 않는다. 해당 과거 엔진의 온전한 원본을 새 코드에 무단 치환하지 않고, 현재 출시 4관문 혼합 예측기 및 사전 봉인 기능에 **확인된 지급·사용 이력만 입력할 수 있는 안전한 인터페이스**를 추가했다.

